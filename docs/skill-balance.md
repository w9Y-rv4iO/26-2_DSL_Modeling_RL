# 액티브 어빌리티 밸런스 — 다이얼, 스윕, 선택한 튜닝

대상: `tag_game/skills.py`의 4종 어빌리티(runner `journey`/`rewind`, tagger
`stasis`/`destiny`). §1-6은 이 4종에 대한 확정 스터디. §7은 `character_3`
(wall/dash)의 1차 측정으로, 아직 튜닝도 ablation도 없는 별개 항목 — 본문과
섞어 읽지 말 것.

## 목표 지표 (등록된 것)

`docs/study-e-protocol.md` §2가 등록한 지표는 **맵별** `balance_error =
|runner_win_rate − 0.5|`. 집계는 7맵 **평균 |err|**(부수적으로 median/max/RMSE).

승률의 평균이 아님. 차이는 형식적이지 않음 — 평균 승률에서는 `Spiral` 0.871의
초과가 `Warren` 0.100의 미달을 **상쇄**하지만, 등록 지표에서는 두 오차가
**합산**됨. 1·2차 패스는 평균 승률로 선택했고, 그래서 등록 지표에서 더 나쁜
튜닝을 "역대 최고"로 보고했음:

| 패스 | 평균 WR | \|평균 WR − 0.5\| | **평균 \|err\| (등록 지표)** |
|---|---|---|---|
| skills off | 0.348 | 0.152 | **0.188** |
| 출시 스펙 | 0.140 | 0.360 | 0.360 |
| 1차 최종 | 0.401 | 0.099 | 0.215 |
| 2차 최종(평균 WR 기준 "최선") | 0.458 | 0.042 | **0.240** |

3차 패스는 등록 지표로 재선택했고, 결론이 바뀜. 4차 패스(§5)는 그 3차 결론이
`destiny`를 삭제하는 것이었다는 사실 자체를 결함으로 보고 어빌리티를 재설계했고,
결론이 다시 바뀜.

**결론 먼저 (4차, §5): `destiny`를 살린 채로 등록 지표를 달성함.** 게이트에
채널링(`DESTINY_CHANNEL`)을 붙여 커밋 비용을 만들고, 러너에게 피탐지 경고
(`Agent.revealed_timer`)를 주고, 착지점을 캐스트 시점이 아니라 **해소 시점**에
계산하도록 바꿈. 7맵 n=240 평균 |err| **0.188(skills off) → 0.146(권장 §1.1)**,
게이트 **해소** 0.44-1.02회/round(이전 0.08-0.16), destiny를 빼면 지표가
**나빠짐**(0.146 → 0.151). 목표였던 0.12에는 **미달**이며 그 잔차는 두 맵의
기하 문제임(§5.6).

3차 결론(`DESTINY_REVEAL: 0.0`, 평균 |err| 0.078)은 **기각**됨 — 수치는 더 좋으나
어빌리티 4종 중 1종이 죽은 상태였음(§1.2, §5.1).

## 1. 권장 설정

### 1.1 권장 — 4차, destiny 살아 있음 (붙여넣기용)

```python
skill_tuning = {
    "DESTINY_CHANNEL": 1.5,        # 신규 다이얼 (게이트 채널링)
    "DESTINY_REVEAL": 2.0,         # 4.0 -> 2.0
    "STASIS_DURATION": 0.6,        # 1.2 -> 0.6
    "REWIND_COOLDOWN": 5.0,        # 30  -> 5
    "REWIND_UNTARGETABLE": 1.0,    # 0.5 -> 1.0
    "JOURNEY_COOLDOWN": 10.0,      # 25  -> 10
}
```

- 근거·측정·ablation은 §5. 7맵 n=240(120 s): 평균 |err| **0.146**, median 0.150,
  max 0.233, RMS 0.160, balanced 1/7, 평균 WR 0.536, 라운드 23.2 s (§5.4)
- 5차(§6)에서 `destiny_landing`의 추첨을 고친 뒤 **같은 dict를 재측정**:
  n=240(120 s) 평균 |err| **0.141**, median 0.158, max 0.208, RMS 0.152,
  평균 WR 0.530. 0.146과 paired 노이즈 안에서 동일하며, dict는 그대로임
  (캐시 v4, §6.1)
- 4종 전부 살아 있음: 게이트 **해소** 0.44-1.02/round(3차 0.08-0.16), stasis
  1.02-1.17, rewind 1.69-3.15, journey 0.27-2.50
- destiny를 제거하면 지표가 **나빠짐**(0.146 → 0.151, n=240; 0.119 → 0.185,
  n=24). 3차에서는 제거가 0.089만큼 이득이었음 → 부호가 뒤집힘. 단 n=240에서의
  크기는 0과 구별 불가이므로 정확한 표현은 **"균형 중립"**(§5.5)
- 목표 0.12에는 미달. 잔차는 `Warren`·`Twins`(미달) vs `Spiral`·`Foundry`(초과)의
  반대 방향 오차이고 전역 다이얼로는 0.125 근처가 한계(§5.6)
- 6개 다이얼을 움직이지만 전부 기존 튜닝 표면. `KITS`·액션 공간·skills-off
  동작은 불변

### 1.2 기각 — 3차 권장 (destiny를 다이얼로 삭제)

```python
skill_tuning = {"REWIND_COOLDOWN": 8.0, "DESTINY_REVEAL": 0.0}
```

- 7맵 n=240: 평균 |err| **0.078**, median 0.029, max 0.300, RMSE 0.123,
  평균 WR 0.436, 라운드 25.0 s. 등록 지표만 보면 §1.1보다 좋음
- **기각 이유**: `DESTINY_REVEAL: 0.0`은 destiny를 다이얼로 죽이는 것. 게이트
  조준에는 시야가 필요하고(`ChasePolicy`는 `can_see`가 참일 때만 2단계를 씀)
  reveal이 0이면 맨션급 맵에서 그 조건이 거의 성립하지 않음 → arm
  0.39-1.31/round, gate 0.08-0.16/round로 사실상 자기 쿨다운만 태움. 정직하게
  말해 **"destiny를 쓰지 말라"를 다이얼로 표현한 것**이며, 그래서 §1.3의
  킷 제거안과 수치가 거의 같음. 프로젝트가 구현하기로 한 4종 중 1종을 삭제하는
  설정을 "달성"으로 보고할 수 없음 → 어빌리티를 고치는 쪽을 택함(§5)
- `DESTINY_COOLDOWN`을 90으로 함께 올려도 n=24 결과가 **완전히 동일**(0.101).
  reveal이 0이면 쿨다운은 아무것도 제약하지 않음

### 1.3 더 좋지만 스펙 변경 (destiny를 킷에서 제거)

```python
KITS[TAGGER] = (STASIS,)              # destiny 제거 — 스펙 변경
skill_tuning = {"REWIND_COOLDOWN": 8.0}
```

- 7맵 n=240: 평균 |err| **0.065**, median 0.013, max 0.308, RMSE 0.122,
  평균 WR 0.437, 라운드 25.0 s. 7맵 중 4맵이 0.487-0.508
- **채택하지 않은 이유**: `KITS`는 RL 액션 인덱스의 정의(action 9 = kit[0],
  10 = kit[1])이므로 tagger 킷을 1개로 줄이면 액션 공간이 11 → 10으로 바뀌고
  기존 11-action 체크포인트가 전부 무효가 됨. `skills.py` 상단 주석의
  "킷에는 추가만, 재배치 금지" 규칙이 그 이유. 순수 다이얼(§1.1)이 0.013 pp
  차이로 같은 일을 하므로, 스펙 변경은 **학습을 다시 돌릴 때만** 권장
- 두 설정의 차이는 "destiny가 arm되고 무효로 만료되는가"뿐. 그 만료가 태거의
  45 s를 태우므로 §1.2가 미세하게 나쁠 이유도, 좋을 이유도 됨(측정상 +0.013)
- 4차(§5) 이후로는 이 항목의 전제 자체가 사라짐 — destiny가 지표에 **기여**하므로
  제거할 이유가 없음

### 1.4 기각된 후보

| 후보 | n=240 평균 \|err\| | 기각 이유 |
|---|---|---|
| skills off | 0.188 | 기준선. 어빌리티가 주는 게임플레이 가치가 0 |

## 2. 2차 개정 — 세 결함과 수정 효과

측정 이전의 문제. 1차 스윕이 "밸런스"로 보고한 수치 중 셋은 엔진·휴리스틱
결함이었음.

### 2.1 실패한 캐스트가 그 틱의 이동을 먹던 문제 (엔진)

- `World.step`이 어빌리티를 이동보다 먼저 처리하면서 **성공 여부를 알기 전에**
  intent를 0으로 만듦. 성공한 캐스트가 이동을 소비하는 것은 의도(그래야
  `Agent.facing`이 고정되고 `journey`가 보던 벽을 팜)지만 실패에도 적용됨
- 수정: `activate()`가 True일 때만 이동을 소비. 실패 시 호출자가 준 (dx, dy)로
  그대로 이동. 휴리스틱 둘 다 3-slot을 `(dx, dy, ability)`로 채워 보냄
  (이전엔 `(0, 0, ability)`). RL 액션 9/10은 이동 성분이 원래 (0,0)이므로 무변화
- 계측 추가: `World.cast_attempts` / `cast_refusals` (`{role: {ability: n}}`),
  `cast_attempt_count()` / `cast_refusal_count()`, `("cast_refused", role,
  ability)` 이벤트. 스윕 리포트의 모든 행이 asks/refusals를 출력

측정(`stalls` 스테이지, `STASIS_RANGE` 120 px = 3타일, Lv3):

| | before | after |
|---|---|---|
| stasis 요청/round | 127.3 | 0.9 |
| stasis 거부/round | 127.0 | **0.0** |
| 태거 이동 | — (라운드의 약 37 %를 정지) | 100.4타일 / 17.9 s = **5.60타일/s** |
| 같은 지표(기본 사거리) | — | 133.9타일 / 24.3 s = 5.51타일/s |
| 3맵 평균 러너 WR | 0.444 (기본 사거리 0.264 → **+18 pp**) | **0.236** |

1차 스윕의 "사거리를 줄이면 러너가 +18 pp"는 전부 정지의 측정치였고, 정지를
없애면 부호가 뒤집힘 — 사거리 축소는 **태거 버프**임(§2.2).

### 2.2 `STASIS_RANGE`·destiny 밴드가 죽은 다이얼이던 문제 (정책)

- `ChasePolicy.STASIS_CAST = TILE * 4.5` 하드코딩, `DESTINY_MAX_DIST` 모듈
  전역 import → 엔진에 넘긴 다이얼이 정책에 도달하지 않음
- 수정: `agents._tuning(world)` (= `getattr(world, "skill_tuning", None)`)로
  라운드의 실제 값을 읽음. 캐스트 거리 = `STASIS_RANGE − STASIS_SLACK`
  (0.5타일, 기본값 5타일에서 정확히 옛 4.5타일 → 출시 라운드 불변). 게이트
  소비 조건은 `tuning.DESTINY_MAX_DIST`와 비교

`STASIS_RANGE` 3맵(Lv3/Warren/Loops) n=24 평균 WR:

| STASIS_RANGE | before | after |
|---|---|---|
| 120 px (3타일) | 0.444 *(정지 아티팩트)* | 0.236 |
| 180 px (4.5타일) | 0.264 | 0.417 |
| 200 px (5타일, 출시) | 0.264 | 0.403 |
| 320 px (8타일) | 0.264 | 0.417 |

- before의 180/200/320은 승률·길이·캐스트 수까지 **비트 단위로 동일**했음.
  after는 서로 다른 라운드(Lv3 라운드 길이 20.9 / 21.9 / 23.4 s, 캐스트 수도 상이)
- 7맵 n=24 평균 WR로는 단조: 120 0.250 / 160 0.387 / 200 0.429 / 280 0.423
- 5타일 이상에서 포화하는 이유가 바뀜: 하드코딩이 아니라 **시야**. 태거 시야가
  7타일이고 캐스트에 `can_see`가 필요하므로 280 px(7타일) 이상은 시야가 제약.
  아티팩트가 아니라 설계상의 상한
- 방향이 직관과 반대: 사거리를 줄이면 태거가 **강해짐**. 정책이 사거리에
  들어오는 즉시 쏘므로 사거리는 사실상 "캐스트 타이밍" 다이얼

destiny 밴드 (7맵 n=24, base = 1·2차 dict):

| 밴드 MIN/PREF/MAX | before | after |
|---|---|---|
| 3/4/5 (기본) | 0.405 | 0.429 |
| 5/6/8 | — | 0.423 |
| 8/10/13 | +12 pp 상승 & destiny ablation 부호 역전 *(아티팩트)* | 0.440 |

밴드는 이제 거의 무효(±1 pp). "밴드를 밀면 러너가 +12 pp"라는 1차 결론은 태거가
*잡으려던 러너에게서 스스로 멀어지던* 텔레포트의 측정치였고, 사라짐.

### 2.3 `journey`의 캐스트 시점 (정책)

- 원인은 튜닝이 아니라 캐스트 시점. 통로는 대칭(Bard E)이고 `FleePolicy`는
  궁지에 몰린 순간에만 팠으므로, 태거가 이미 그 방향에 있을 때만 굴이 열림 →
  러너가 추격자에게 지름길을 선물
- 수정: `FleePolicy._journey_plan` — 궁지 여부와 무관하게 **가격제**
  1. 현재 목표(스테이션/출구, 패닉 시 도주 목표)까지의 BFS 경로를
     `JOURNEY_GAIN`(=4)타일 이상 단축해야 함
  2. 태거의 **마지막 목격 위치**가 굴의 반대편 입구까지 나보다
     `JOURNEY_SAFE_MARGIN`(=2)타일 이상 멀어야 함
- 비용: 굴은 `a`(벽 앞 열린 타일)와 `b`(벽 뒤 이미 걷는 타일)를 잇고 타일이
  일직선·4-연결이므로 단축량이 `d(me→a) + (len+1) + d(b→goal)`로 **정확히**
  계산됨 → 새 BFS 없이 이미 있는 두 필드(월드가 `wall_epoch`로 메모)만 씀.
  후보는 4개 기수방위뿐(대각 3칸은 4-연결이 아니라 `bfs_distances`가 통과 못 함)
- castability는 확실히 개선: 1차에서 사실상 캐스트가 없던 `Twins` 0.10 /
  `Foundry` 0.07이 **0.89 / 0.37**(풀 킷 n=240). 권장 설정에서는 5맵이
  0.55-1.86, `Lv3` 0.22 / `Foundry` 0.17 (§3.3)
- **엔진 변경은 하지 않음**: (a) `JOURNEY_DEPTH` 3 → 2는 반대 효과(depth는
  상한이므로 1-2타일 벽은 이미 후보, 2로 내리면 3타일 벽이 빠짐), (b) 태거
  통과 시 조기 붕괴 / (c) runner 전용은 정책 수정만으로 목표가 달성되어
  불필요하며 HUD·관측까지 건드리는 스펙 변경

## 3. 3차 재선택 (등록 지표)

### 3.1 프로토콜

- 드라이버 `scripts/skill_sweep.py`. 모든 스테이지가 이제 `mean|e| / med /
  max / rmse`를 함께 출력(`err_stats`) — 잘못된 집계로 다시 읽히지 않게
- 탐색 `episodes=24, round_time=60` (7맵 22점), 확정 `episodes=240,
  round_time=120` (6점). 워커 4개, 캐시 on
- 캐시 세대 분리: 캐시 키는 맵+프로토콜+튜닝+정책knob이고 **코드 버전이 아님**.
  §2의 수정으로 1차 엔트리는 무효 → 2·3차는 `results/skill_sweep_cache_v2`,
  1차는 before 열의 원자료로 보존
- 어빌리티 제거는 끝나지 않는 쿨다운(1e9)을 라운드 시작에 심는 방식. 두 휴리스틱
  모두 `state.ready()`로 게이트하므로 "킷에 없음"과 동일

### 3.2 탐색 (n=24, 7맵, 평균 \|err\| 오름차순)

| 후보 | 튜닝 | 제거 | 평균 \|err\| | med | WR |
|---|---|---|---|---|---|
| R2 | `REWIND_COOLDOWN` 8 | destiny | **0.095** | 0.042 | 0.417 |
| R4 | rewind 12 + `STASIS_RANGE` 160 | destiny | 0.107 | 0.083 | 0.417 |

## 5. 4차 — `destiny` 재설계 (채널링 + 피탐지 경고)

### 5.1 진단 — 3차의 "성공"이 왜 실패인가

- 3차 권장안 `DESTINY_REVEAL: 0.0`은 등록 지표 0.078을 냈지만, 그 메커니즘은
  **게이트를 조준 불가로 만드는 것**이었음: arm 0.39-1.31/round에 gate
  0.08-0.16/round. 즉 4종 중 1종을 다이얼로 삭제한 설정
- 더 나쁜 것은 부호: 풀 킷에서 destiny만 빼면 n=24 0.214 → 0.125, `Warren`
  0.208 → 0.500, `Atrium` 0.125 → 0.333. **이미 태거 우세인 맵에서 destiny가
  가장 강함** → 줄여야 할 오차를 키우는 어빌리티였음
- 원인은 튜닝이 아니라 메커니즘. 게이트가 **즉발·무경고·개입 불가**였음:
  - 러너는 reveal된 사실을 알 수 없었음(관측에도 슬롯이 없었음)
  - 캐스트 즉시 텔레포트 → 반응 시간 0
  - 태거가 지불하는 비용은 쿨다운뿐 → "무료 재배치"
- LoL의 원본은 2단계 + **커밋 비용**(Gate는 채널링이고 적이 보고 반응함). 우리
  구현은 2단계만 가져오고 비용을 뺐음. 4차는 그 비용을 되돌려 놓음

### 5.2 변경 사항 (메커니즘)

| 항목 | 이전 | 이후 |
|---|---|---|
| 2단계 캐스트 | 즉시 텔레포트 | `DESTINY_CHANNEL`(기본 1.5 s) 채널 시작 |
| 채널 중 태거 | — | **이동 불가·캐스트 불가** (intent 폐기, `facing`도 고정) |
| 착지점 계산 | 캐스트 시점 | **해소 시점** (`resolve_destiny_gate` → `destiny_landing`) |
| 인터럽트 | 없음 | **arm 윈도가 만료되면 채널 포기**(쿨다운은 이미 청구됨) |
| 러너 인지 | 없음 | `Agent.revealed_timer`(= reveal과 동일 길이) + `World.gate_channeling()` |
| 러너 정책 | 없음 | `FleePolicy`: 표식 + 채널 동시 성립 시 **재배치**(스테이션 채널링 중단) |
| 태거 정책 | 밴드 안쪽이면 안 씀 | 위 + **채널이 걷는 것보다 나아야 함**(`_gate_bar`) + 윈도 부족 시 안 씀 |
| 관측 | `SKILL_SIZE` 7 | **9** (슬롯 7 = 역할별 위협 플래그, 8 = 게이트 채널 시계) |

- `_gate_bar = DESTINY_MAX_DIST + me.speed * DESTINY_CHANNEL / TILE`. 기본값에서
  5 + 7.5 ≈ 12.5타일 → "곧 잡을 러너에게는 게이트를 쓰지 않음"이 다이얼에서
  파생되는 규칙이 됨. `DESTINY_CHANNEL: 0`이면 옛 즉발 게이트와 비트 단위로 동일
- 인터럽트를 arm 윈도 하나로 제한한 이유: 러너에게 공격 수단이 없으므로(데미지·CC
  없음) "러너가 끊는다"를 구현할 대상이 없음. 러너의 반격 수단은 **1.5 s 그 자체**
  (재배치 + 태거의 정지). 해소 시점에 시야를 재요구하는 안은 기각 — CLOAK 아이템만
  관여하고 밸런스 스윕은 `items_enabled=False`라 측정 자체가 불가능
- `DESTINY_CHANNEL >= DESTINY_ARM_TIME`은 생성자에서 거부. 윈도 안에 끝낼 수 없는
  채널은 "어빌리티 삭제"를 다이얼로 쓴 것이고, 그게 이 재설계가 되돌린 실수임

  240-시드 리스트에 과적합되지 않음, (ii) 최악 맵이 더 좋음(max 0.233 vs 0.283,
  `Atrium` 0.025 vs 0.283). 0.8의 장점은 `n_balanced` 3/7

### 5.5 One-out ablation (등록 지표, 권장 §1.1 튜닝)

제거 시 평균 \|err\|가 **올라가면** 그 어빌리티는 균형에 기여함.

| 제거한 어빌리티 | n=24 평균 \|err\| | 기여 (제거 − 유지) | n=240 |
|---|---|---|---|
| (없음, 풀 킷) | 0.119 | — | 0.146 |
| `journey` | 0.137 | +0.018 | — |
| `rewind` | 0.458 | **+0.339** | — |
| `stasis` | 0.196 | +0.077 | — |
| `destiny` | 0.185 | +0.066 | 0.151 → **+0.005** |

- **핵심: destiny를 제거하면 지표가 나빠짐.** 3차에서는 정반대였음(풀 킷 0.214 →
  destiny 제거 0.125, 즉 −0.089). 부호가 뒤집혔고, 이것이 재설계의 판정 기준
- 단 n=240에서의 크기는 **+0.005로 0과 구별 불가**. 정직한 표현은 "destiny가
  균형에 기여한다"보다 **"destiny가 균형 중립이 되었다"** 임. 3차의 −0.089에서
  중립으로 온 것이 성과이고, 그 이상은 주장하지 않음
- destiny 제거의 진짜 효과는 평균 WR 0.536 → 0.651이고, 오차가 비슷한 이유는
  7맵이 통째로 0.60-0.73으로 **과잉** 이동하기 때문. 즉 destiny는 이제 킷 전체의
  러너 편향을 되돌리는 균형추 역할을 함
- `rewind`(+0.339)가 압도적. `REWIND_COOLDOWN` 5 s가 이 튜닝의 축이며, 빼면 러너
  WR 0.042로 붕괴. 4종 중 어느 것도 제거가 이득이 아님 — 4차 튜닝에서 처음 성립

### 5.6 4차 한계

- **목표 0.12 미달 (0.146).** 잔차의 구조는 명확함: `Warren` 0.267 / `Twins`
  0.350(미달)과 `Spiral` 0.725 / `Foundry` 0.658 / `Loops` 0.621(초과)이 **반대
  방향**이라 전역 다이얼로 동시에 못 고침. n=240 데이터로 계산하면 균일한 태거
  버프 δWR=0.08-0.12를 가해도 평균 \|err\|는 0.125-0.127에서 멈춤(`STASIS_DURATION`
  0.8이 그 예측의 실측치 0.140). 남은 축은 맵 기하 또는 맵별 튜닝(과적합)
- **게이트의 힘은 근접이 아니라 정보**: 밴드를 3-5 → 10-16으로 밀어도 지표가
  ±0.01(§5.3). reveal 4.0 → 2.0이 destiny를 가장 크게 약화시킴. 따라서 destiny의
  균형은 결국 "정보를 얼마나 줄 것인가"이고, 채널링은 그 정보의 **환금 비용**을
  만든 것. 이 엔진에서 destiny를 균형 *양*으로 만들려면 reveal을 더 줄여야 하고,
  그러면 다시 조준 불가 쪽으로 돌아감 — 중립이 사실상 상한으로 보임
- **`DESTINY_COLD`(정책)가 가장 강한 미사용 레버**: 라운드 길이와 맵 불균형이
  상관되어 있어(태거 우세 맵은 11-18 s에 끝남) "차가워진 뒤에만 arm"을 16-24 s로
  올리면 destiny가 짧은 맵에서만 사라져 오차가 줄어듦(0.167). 채택하지 않은 이유는
  gate 해소가 0.00-0.42/round로 붕괴해 §1.2와 같은 삭제가 되기 때문. 기록해 두는
  이유: 이 레버는 "어빌리티를 맵 길이에 조건화한다"는 설계 아이디어이고, 삭제가
  아닌 형태로 다시 쓸 여지가 있음
- 라운드 길이는 skills-off 40.1 s → 23.2 s (−42 %). `REWIND_COOLDOWN` 5 s가
  만드는 즉시 해소형 교전 때문이며 등록 지표에는 들어가지 않는 비용. destiny를
  빼면 30.6 s로 회복됨
- 러너 재배치 규칙(`FleePolicy.RELOCATE_ON_GATE`)은 **표식 + 채널이 동시 성립**할
  때만 발동. 모든 스윕 설정에서 `DESTINY_REVEAL > DESTINY_CHANNEL`이므로 실질
  조건은 채널 하나뿐이지만, reveal을 채널보다 짧게 튜닝하면 러너가 채널 중간에
  단서를 잃음 — 짧은 reveal을 사는 대가로 의도한 것
- 전부 heuristic vs heuristic. 학습 정책은 슬롯 53/54(피탐지·채널 시계)를 직접
  보므로 여기의 휴리스틱 반격보다 잘할 수도, 못할 수도 있음 → 학습 결과로
  재측정 필요. 관측 폭이 53 → 55로 바뀌었으므로 skills-ON 체크포인트는 재학습
  대상(레포에는 해당 파일이 없음)
- 탐색 순서가 확정 단계에서 유지되지 않았음: n=24 0.119 → n=240 0.146. 60 s
  클럭이 `Spiral`의 교착을 escape로 바꾸지 못하는 것(문서 §프로토콜의 알려진
  편향)이 주원인. 4차의 모든 n=24 수치는 **탐색값**이며 결과로 인용 불가
- `docs/study-e-protocol.md` §2는 수정하지 않았음

### 6.1 `DESTINY_MIN_DIST` — 죽은 다이얼이었음

- 원인: `World.destiny_landing`이 `DESTINY_PREFERRED_DIST` 거리의 후보가 하나라도
  있으면 풀을 **그 거리로만** 좁혔음(흡수 필터). 13맵 4,895개 floor 위치를 전수
  조사한 결과 preferred 거리 후보가 **없는 위치가 0개** → 밴드 하단이 추첨에
  들어갈 일이 없었음. `__post_init__`이 `MIN > PREFERRED`도 금지하므로 위로도 불가
- 증거(궤적 해시, 7맵 × 6시드 × 900틱, base = §1.1 튜닝, `skill_sweep.py dials`):

| 다이얼 | 값 | before 해시 | after 해시 |
|---|---|---|---|
| (base) | — | `dff0093d1522` | `f6adfeb31142` |
| `DESTINY_MIN_DIST` | 1 | `dff0093d1522` **(= base)** | `a545d6da9a04` |
| `DESTINY_MIN_DIST` | 4 | `dff0093d1522` **(= base)** | `cad312dda9fa` |
| `DESTINY_MAX_DIST` | 4 / 8 | `80555de7f583` / `112b42ee26d0` | `81055cc185e3` / `d55a6da8b338` |
| `STASIS_RANGE` | 120 / 320 | `4d3fd20260b6` / `ad3c5f7c900d` | `5ab0ac927d7c` / `bb5489408111` |
| `REWIND_DELAY` | 2 / 8 | `c57d13910816` / `5ba550ce1fe1` | `2281ab143418` / `71f2606d8d1e` |

- 수정: 밴드 전체에서 추첨하고 preferred는 **가중치**로만 반영.
  `w(d) = 1 / (1 + |d − PREFERRED|)` → 기본 3/4/5 밴드에서 타일당 0.5 / 1 / 0.5.
  Arena 스폰에서 각 링이 3타일이라 200회 추첨이 44 / 105 / 51로 갈림
  (`test_destiny_draw_prefers_but_does_not_filter`). RNG 소비는 `choice`와 동일한
  **1회**(`random()`) — 밴드 폭이 시드 오프셋이 되면 skills-ON A/B가 서로 다른
  RNG 스트림 비교가 됨
- 권장 튜닝(§1.1)에 대한 영향: 탐색 n=24 0.119 → **0.149**, 확정 n=240/120
  0.146 → **0.141**. 확정값이 기준이고 paired SE ≈ 0.01-0.02이므로 **동일**로
  읽어야 함. dict 변경 없음
- 이제 살아 있는 다이얼로서의 값(§1.1 base, 7맵): `MIN` 1 / 3 / 4 →
  n=24 평균 \|err\| **0.071** / 0.149 / 0.179. 단 `MIN` 1을 n=240/120으로 확정하면
  **0.138** vs 기본 0.141 → 구별 불가. 즉 n=24의 0.071은 탐색 노이즈이고
  권장안 변경 근거가 되지 못함(4차 §5.6의 "밴드는 정보가 아니라 거리이므로 거의
  무효"라는 결론은 유지)

### 6.2 `REWIND_MAX_SAMPLES` — 튜닝된 `REWIND_DELAY`를 따라가지 않았음

- 프룬은 타임스탬프 기준인데 `deque(maxlen=...)`은 고정 600이었음. 600 샘플은
  60 Hz에서 10 s, 15 Hz에서 40 s → 딜레이를 올리면 **조용히** 되감기가 짧아짐
- 측정(수정 전): `REWIND_DELAY: 12.0` @60 Hz → 실제 **9.98 s**,
  `REWIND_DELAY: 45.0` @15 Hz → **39.93 s**
- 수정: `SkillTuning.max_samples` = `history_seconds × REWIND_SAMPLE_HZ + 2`,
  하한 600, 상한 20,000. `REWIND_SAMPLE_HZ = 120`(60 Hz 클라이언트의 2배,
  `main.py`의 dt 클램프 1/30의 4배). 기본 5 s 윈도에서 5 × 120 = 600이므로
  출시 라운드는 불변. 테스트는 15 Hz·60 Hz × 딜레이 12 s·45 s 4조합
  (`test_rewind_buffer_follows_a_tuned_delay`)
- **기록된 스윕 수치 중 무효인 것은 없음**: `mapstudy/results/skill_tuning.json`의
  `REWIND_DELAY` 최대값은 **6.0**(12개 지점)이고 모든 스윕은 15 Hz(dt = 1/15)라
  600 샘플 = 40 s ≫ 7 s. 즉 이 결함은 스윕에는 닿지 않았고, 60 Hz 클라이언트에서
  `REWIND_DELAY > 10`을 튜닝했을 때만 발현됨(출시 두 튜닝은 4.0)

### 6.3 `JOURNEY_DEPTH` — "효과 0"이 아니었음

- 기존 주석: "5로 올리면 7맵 결과가 0만큼 변함 — 4-5타일 벽으로 두 열린 영역이
  갈리는 맵이 없음". **틀림**. `Loops`가 그런 맵임
- 측정(§1.1 base, 7맵, 캐시 v4):

| 2 | 0.161 | — | `Loops` 0.667 → 0.750 (n=24) |
| **3 (기본)** | **0.149** | **0.141** | — |

  효과 전체가 `Loops` 한 맵의 기하이고 0.004는 paired 노이즈 안 → 권장 튜닝에
  **넣지 않음**. 다만 "효과 0"은 삭제하고 실측치로 교체함

### 6.4 `destiny_fizzled` (방어적) vs `destiny_lapsed` (실제로 발생)

### 6.6 주석 산술 정정 (측정 없이 고친 것)

- `stasis`: "1.2 s는 러너가 6타일을 빠져나가는 1.5 s보다 짧다" → 6타일은 240 px,
  240 px/s에서 **1.0 s**. 실제 관계는 1.2 s = 태거 240 px(6타일) 무료 접근,
  러너 288 px(7.2타일) 손실 → **이긴 추격을 굳히는 게 아니라 추격을 만든다**.
  Lv3 20시드에서 as-designed 킷이 태거 +10 pp인 근거와 일치
- `stasis` 사거리: "5타일은 태거 7타일 시야의 한 타일 안" → **두 타일** 안
- `rewind`: "4 s @240 px/s는 6타일에서 24 px 부족" → 4 × 240 = 960 px = **24타일**.
  4 s는 속도차 40 px/s 기준으로는 **4타일**이므로 두 수를 다 적음
- ablation 부호: `기여 = (제거 시 평균|err|) − (유지 시 평균|err|)`, **양수면 그
  어빌리티가 균형에 기여**. §5.5·`skill_tuning.json`의 `note`와 동일하고,
  `skills.py`의 `DESTINY_CHANNEL` 주석만 반대 부호를 쓰고 있었음(3차 destiny
  ablation은 −0.089)
- `FleePolicy.JOURNEY_GAIN` 표: 세 값이 서로 다른 base에서 측정된 것이었음.
  base별로 분리하고 각 행에 `skill_tuning.json` 키를 적음(base R =
  `{REWIND_COOLDOWN: 12}` → 4/6/journey-off 0.107/0.119/0.149, base E = 3다이얼
  → 4/8/journey-off 0.125/0.149/0.137). base 안에서 읽으면 결론(=4)은 유지
- "60 s 라운드의 약 8 s 정지" → 정지 8.5 s는 **17.9-23.2 s 라운드의 37 %**이고
  60 s는 라운드 **제한 시간**임(§2.1). `skills.py`·`world.py`·`skill_sweep.py`
  세 곳 통일
- `skills.py`의 `COOLDOWNS` dict 삭제 — 어디서도 읽지 않으면서 네 쿨다운의
  두 번째 사본이었음. 유일한 출처는 `SkillTuning.cooldown()`
- `agents.py`의 `getattr(world, ...)` 기본값 6곳 삭제 — `World.__init__`이
  `wall_epoch`·`skills_enabled`·`skill_tuning`을 무조건 설정하므로 도달 불가
  기본값이었고, 속성명이 바뀌면 조용히 skills-OFF로 읽히는 위험만 남음

## 7. `character_3` (wall/dash)와 킷 배치 — 1차 측정 (미확정)

`Add selectable characters` 커밋(`tag_game/world.py`, `characters=`)으로 어느
역할이든 `tag_game.skills.CHARACTERS`의 어느 킷이든 장착할 수 있게 됨. 세 번째
캐릭터 `character_3 = (wall, dash)`는 그 커밋 시점에 "밸런스 데이터 없음"으로
출시됨 — 스킬 자체가 아니라 **측정 도구가 없었기 때문**: `mapstudy/balance.py`의
`rollout`/`evaluate`가 `characters` 인자를 몰라서 `World`에 킷을 지정해 돌릴
방법이 아예 없었음. 이번에 그 인자를 추가(`protocol_key`의 캐시 키에도 반영,
기본 페어링일 때는 키에 안 들어가므로 §1-6의 기존 캐시 엔트리는 전부 그대로
유효)한 뒤 처음 돌린 수치가 이 절.

**§1-6과 다른 점 — 섞어서 인용하지 말 것:**
- `scripts/skill_sweep.py`가 아니라 `mapstudy.balance.evaluate`를 직접 호출한
  임시 스크립트로 측정. 따라서 캐스트/거부 계측, ablation, 궤적 해시 생존성
  검증(§6.5 같은 것)이 전혀 없음 — 이 절에 있는 건 승률과 그로부터 유도되는
  수치뿐
- 튜닝 다이얼을 전혀 움직이지 않음. `WALL_DURATION=6.0` /
  `WALL_COOLDOWN=15.0` / `DASH_DISTANCE=1.5` / `DASH_DURATION=0.15` /
  `DASH_COOLDOWN=10.0`, 전부 `tag_game/skills.py`의 as-designed 기본값
- 대칭 케이스(양쪽 다 `character_3`)만 측정. `character_3` vs 기존 킷(비대칭
  매치업)은 아직 없음
- `ChasePolicy`/`FleePolicy`는 wall·dash 전용 전술이 없음 — journey/rewind/
  stasis/destiny처럼 손으로 튜닝된 로직이 아니라 `agents.py`의
  `_generic_ability`(태그 기반 제네릭 폴백)로만 캐스팅함. 즉 이 절의 수치는
  "이 스킬셋의 상한"이 아니라 "손대지 않은 AI가 쓸 때의 하한"에 가까움

### 7.2 역배치 실험 — 원인은 역할이 아니라 킷의 어빌리티 카테고리

`character_3`가 좋은 숫자를 낸 게 "wall/dash 설계가 훌륭해서"인지, 아니면
"태거한테서 cc/engage 수단(stasis/destiny)이 빠져서"인지 §7.1만으로는 구분 안
됨 — 두 변수(태거라는 역할, cc/engage 카테고리 보유)가 §머리말 표의 기존 킷에서
항상 같이 붙어 있었기 때문. 분리하려고 **역배치**를 돌림: 태거가
`character_1`(journey+rewind, terrain/escape), 러너가 `character_2`(stasis+
destiny, cc/engage) — 출시 배정의 완전한 대칭. `character3_both`와 같은 이유로
`ChasePolicy`/`FleePolicy` 둘 다 자기 킷이 아니라서 제네릭 폴백만 씀 — 그래서
직접 비교 가능.

| 조건 | cc/engage(stasis/destiny) 보유자 | mean\|err\| | balanced | 평균 WR |
|---|---|---|---|---|
| skills off | 아무도 없음 | 0.188 | 1/7 | 0.348 |
| 기존 킷(출시) | **태거** | 0.372 | 0/7 | **0.128** |
| `character_3` 양쪽 | 아무도 없음 | 0.137 | 3/7 | 0.376 |
| **역배치** | **러너** | 0.135 | 1/7 | **0.501** |

맵별 `balance_error` / `runner_win_rate` (역배치, n=240):

| 맵 | err | wr | decisive |
|---|---|---|---|
| Lv3 | 0.100 | 0.600 | 예 (러너 쪽으로) |
| Warren | 0.112 | 0.388 | 예 (태거 쪽으로) |
| Twins | **0.013** | 0.487 | 아니오 — 균형과 구분 불가 |
| Loops | 0.129 | 0.629 | 예 (러너 쪽으로) |
| Spiral | 0.071 | 0.571 | 예 (러너 쪽으로) |
| Foundry | 0.175 | 0.675 | 예 (러너 쪽으로) |
| Atrium | 0.342 | 0.158 | 예 (태거 쪽으로, 역시 최악) |

**결론: cc/engage 페어를 쥔 쪽이 이긴다.** 태거가 쥐면 평균 WR 0.128, 아무도
안 쥐면 skills-off 0.348 / `character_3` 0.376, 러너가 쥐면 0.501로 거의 정확히
뒤집힘. §7.1의 "손대지 않은 `character_3`가 두 대조군보다 좋다"는 결과는 그래서
**"wall/dash가 잘 만들어져서"보다 "태거의 가장 강한 지렛대(cc/engage)가 빠져서
원래 있던 태거 우위가 상쇄된 것"**으로 읽는 게 더 정확함.

**단, 평균만 보고 "역배치가 최선"이라 결론 내리면 안 됨:** mean WR 0.501은
맵마다 고르게 균형이라서가 아니라 **반대 방향 오차끼리 평균에서 상쇄**된 결과임
(`aggregate()`가 늘 경고하는 바로 그 함정). 균형과 통계적으로 구분 안 되는 맵은
`Twins` 단 1개(1/7)뿐이고, `Lv3`/`Loops`/`Spiral`/`Foundry`는 오히려 러너 쪽으로
과하게 넘어감(wr 0.57-0.68), `Warren`/`Atrium`은 여전히 태거 쪽. 맵 단위로 보면
`character_3`(3/7 balanced)가 역배치(1/7)보다 더 고르게 균형적임 — "어느 쪽이
cc를 갖든 강한 쏠림이 생긴다"는 것 자체가 stasis/destiny가 as-designed 상태로는
과하게 강하다는 신호(§머리말의 0.360/PLAYABLE_TUNING 필요성과 같은 결론).
