> 나눠 돌렸는지에 대한 역사 기록이다.

Ao Oni 스타일 2D 술래잡기. 술래(빨강, "IT")는 부채꼴 시야로 도망자를 찾아
제한시간(120초) 안에 잡으면 승리. 도망자(파랑)는 맵에 흩어진 **미션**을 전부
완료해 **탈출구(EXIT)** 를 열고 빠져나가면 승리 — 시간이 다 되면 술래 승리.
맵은 **문(door)** 으로 연결된 여러 방으로 구성된다 (Mansion 맵).

## 실행

```bash
python3 -m venv .venv
.venv/bin/pip install pygame
.venv/bin/python main.py
```

## 규칙

- **시야**: 두 캐릭터 모두 부채꼴 시야만 가진다. 술래는 좁고 긴 사냥용 시야
  (120°, 7타일), 도망자는 넓은 경계용 시야(210°, 6타일) + 더 좋은 "청각"
  (근거리 전방위 감지). 시야 밖 상대는 화면에도 보이지 않는다(혼자 플레이 시).
- **미션**: 초록 원 위에서 2초 채널링하면 완료. 전부 완료하면 EXIT가 열린다.
- **문**: 숫자 타일을 밟으면 짝이 되는 숫자 타일(다른 방)로 이동.
- **속도**: 도망자 240 > 술래 200. 잡히는 건 코너/문/매복에서다.
  술래의 rage(시간이 갈수록 가속)는 미션 맵에선 최대 +10%, 클래식 맵 +40%.
- **아이템**: ⚡스피드(1.5x, 2.5초) · C 은신(4초, 상대에게 안 보임) ·
  F 빙결(상대 3초간 50% 감속) · ! 투시(4초, 벽/방 관통으로 상대 위치 표시 —
  단, 은신 중인 상대는 투시로도 안 보임).
- E(탈출구)가 없는 맵은 클래식 룰: 시간까지 생존하면 도망자 승리.

## RL 학습

```bash
.venv/bin/pip install -r requirements.txt

# 자유 실험 (Mansion 셀프플레이 등). --out은 이제 "런 디렉터리"다:
# 최종 가중치는 <out>/model.zip, 학습 곡선은 <out>/progress.csv,
# 중간 스냅샷은 <out>/checkpoints/ 에 쌓인다.
.venv/bin/python train.py --role runner --opponent idle --steps 400000 --out runs/phase_a
.venv/bin/python train.py --role runner --init runs/phase_a/model.zip --steps 1600000

# 술래
.venv/bin/python train.py --role tagger --steps 1000000

# Self-play 세대 교대: 얼려둔 상대 모델을 상대로 계속 학습
.venv/bin/python train.py --role runner --init ppo_runner_mansion.zip \
    --opponent model:ppo_tagger_mansion.zip --steps 800000

# 참고: evaluate.py는 이제 기본이 아이템 OFF(실험 프로토콜과 동일).
# 아이템을 켜고 학습한 옛 Mansion 모델을 재려면 --items를 붙일 것.
.venv/bin/python evaluate.py --role runner --map Mansion --episodes 100 --items
```

게임 메뉴(RL 모드)는 저장소 루트의 `ppo_<role>_<map>.zip`을 자동 로드한다 —
학습한 모델과 놀아보려면: `cp runs/<런>/model.zip ppo_runner_lv3.zip`

Mansion 기준 결과 (60–100 에피소드):

| 매치업 | 결과 |
|---|---|
| 휴리스틱 도망자 vs 휴리스틱 술래 | 술래 전승 — 평균 1.9미션 후 24초에 잡힘 |
| **PPO 도망자** vs 휴리스틱 술래 | 술래 승 — 미션 러시(17초에 1.8미션)하다 잡힘 |
| 휴리스틱 도망자 vs **PPO 술래** | **술래 98% 승** — 미션 3개를 다 내주고 **탈출구 캠핑**을 창발적으로 학습 |
| **PPO 도망자** vs **PPO 술래** | **도망자 100% 승** — 3미션 + 34초 탈출로 캠핑 파훼 |

한 세대 만에 창발적 군비경쟁이 나타났다: 학습된 술래는 추격 대신
탈출구 캠핑(Dead by Daylight식)을 발견했고, 다음 세대 도망자는
속도 우위로 캠핑을 정면 돌파하는 법을 학습했다.

- **관측(46차원, 시야-정직)**: 자기 위치/방/방향, 상대 가시성 + *마지막으로 본*
  위치·경과시간(시야 밖 정보는 관측에 없음), 목표(다음 미션/탈출구)까지의
  방향·거리(문 경유 라우팅), 미션 진행도, 남은 시간, 아이템 상태, 주변 5×5 벽.
- **행동**: Discrete(9) — 정지 + 8방향.
- **보상**: 도망자 = 미션 진행 ×5 + 목표 접근 shaping + 승패 ±10.
  술래 = (문 경유) BFS 거리 좁히기 shaping + 승패 ±10.
- 학습된 모델(`ppo_<role>_<map>.zip`)이 저장소 루트에 있으면 게임 메뉴의
  RL 모드가 자동으로 로드한다.

## 커리큘럼 실험 — 팀 프로토콜

**연구 질문**: 같은 최종 맵(Lv3)에서 평가할 때, 커리큘럼(Lv1→Lv2→Lv3
가중치 이전)이 처음부터 Lv3에서 학습(직접학습)보다 나은가?

### 레벨 시스템

최종 맵 **한 장**(`tag_game/levels.py`의 `FINAL_ROWS`)이 유일한 원본이고,
낮은 레벨은 기능을 **끄는** 방식으로 파생된다. 그래서 세 레벨의 좌표계·스폰
위치가 완전히 같고, 가중치 이전이 의미를 가진다 (관측 벡터 모양도 불변).

| 레벨 | 파생 규칙 | 게임 룰 |
|---|---|---|
| Lv1 | 외곽 벽만, 발전기 X, 탈출구 X | 클래식 술래잡기 — 시간까지 생존하면 승 |
| Lv2 | + 발전기 5개 + 탈출구 4개 | 발전기 전부 수리 → 아무 탈출구로 탈출 |
| Lv3 | + 내부 장애물 (최종 맵) | 위와 동일, 진짜 맵에서 |

- 발전기(`G`) = 미션 스테이션(`M`)과 같은 것. 탈출구(`E`)는 외곽 벽의
  중앙 개구부 4곳 (북/남/서/동) — 어느 곳으로든 탈출 가능.
- **주의 — Lv1은 룰도 바뀐다**: 탈출구가 없으면 엔진이 클래식 룰을
  적용한다. 타임아웃이 도망자 *승리*가 되고(Lv2/Lv3에선 패배), 술래
  rage 상한이 1.4×로 올라간다(미션 맵은 1.1×, 즉 Lv1 후반엔 술래가
  도망자보다 빨라진다). 버그가 아니라 "순수 술래잡기"라는 1단계 정의의
  일부다 — 결과 해석과 발표 때 명시할 것.
- 미리보기: `.venv/bin/python -m tag_game.levels`
- 게임에서 직접 플레이: `main.py` 메뉴에서 `M` 키로 Lv1/Lv2/Lv3 선택.
- 커스텀 ablation (파이썬에서): `TagEnv(role="runner",
  level_config=LevelConfig(generators=True, exits=False, obstacles=True))`
- 개인 학습 설정을 만들 때는 `configs/`의 파일을 복사해서 값만 바꿀 것.
  `train.py`가 아는 키(`steps`/`map`/`items`/`opponent`/`envs`/`round_time`/
  `ckpt_every`/`role`/`ppo`)만 허용하고, 오타 난 키는 학습 시작 전에
  에러로 잡아준다 (`"step"`이라고 쓰고 기본값으로 학습되는 사고 방지).

### 실험 설계 (전원 공통 — 바꾸지 말 것)

- **한 사람 = 한 arm, 시드는 여러 개**: 5명 중 **1명이 직접학습**(최종 맵에서
  바로), **4명이 커리큘럼**(Lv1→Lv2→Lv3 단계별)을 맡는다. **arm은 고정,
  시드만 바꿔 가며 여러 번 돌린다**.
  1라운드(1인 1런)는 필수이고 그 뒤부터가 실험을 실험답게 만드는 부분이다
  (바로 아래 「라운드를 늘리면 생기는 일」). 배정표는
  `configs/team.json`이 원본이고 아래 표는 그 복사본이다.
- **시드는 사람마다 독립 블록.** 기본 시드는 멤버 순서대로
  1~5번을 나눠 갖고, 라운드가 늘 때마다 자기 기본 시드에 +10씩 더한다
  (1 → 11 → 21). 그래서 누구와도 겹칠 수 없다. 같은 arm에 같은 시드를 두 번
  돌리면 설정도 시드도 같아서 **완전히 같은 런**이라 아무것도 늘지 않는다.
- **두 arm, 같은 예산**: 커리큘럼 = Lv1 393,216 + Lv2 589,824 + Lv3
  1,015,808 = 총 1,998,848 스텝(≈200만). 직접학습 = Lv3 1,998,848 스텝.
  숫자가 이상해 보이는 건 PPO 롤아웃 단위(8 env × 2048 = 16,384)의
  배수라서다 — SB3는 롤아웃 단위로만 멈추기 때문에, 이렇게 해야 두 arm이
  스텝 하나까지 정확히 같아진다. (스텝 수는 `configs/*.json`, PPO
  하이퍼파라미터는 `train.py`의 `DEFAULTS` — 한 곳에만 있어서 arm끼리
  어긋날 수 없다.)
- **아이템 OFF**, round 120초, 도망자 학습, 상대는 휴리스틱 술래.
- **공용 평가**: 어느 체크포인트든 같은 프로토콜(Lv3, 고정 시드 200
  에피소드, 아이템 OFF)로 채점. `evaluate.py`가 체크포인트에 기록된 누적
  스텝 수도 출력하므로 예산이 맞는지 서로 검증할 수 있다.
- **예산 일치 지점 3개**: 두 arm을 **끝점 한 번만** 비교하지 않는다.
  스크립트가 자동으로 세 지점을 같은 프로토콜로 채점한다 — 직접학습 arm은
  그 스텝 수의 체크포인트를, 커리큘럼 arm은 그 시점의 단계 모델을 쓴다.

  | 지점 | 누적 스텝 | 커리큘럼 쪽 모델 | 의미 |
  |---|---|---|---|
  | early | 393,216 | Lv1 종료 | 1단계의 **비용** (발전기·탈출구를 아직 못 봄) |
  | mid | 983,040 | Lv2 종료 | **Lv3 경험 0**인 모델 — 여기서 차이가 나면 진짜 전이 |
  | final | 1,998,848 | Lv3 종료 | 헤드라인 |

- **학습 곡선이 기본 산출물**: `scripts/run_*.sh`가 마지막에
  `evaluate.py --curve`를 돌려 체크포인트마다 Lv3 점수를 찍는다. 런이
  한 자릿수인 설계에서 **끝점 몇 개보다 곡선 몇 개가 훨씬 많은 것을 말해
  준다.**
  (헤드라인 결과가 전부 저장된 뒤 마지막에 돌기 때문에 중간에 끊어도
  손해가 없다. `CURVE=0`으로 끄고, `CURVE_EVERY=2`로 절반만 찍을 수 있다 —
  early/mid/final 지점과 양 끝점은 `--every`를 줘도 항상 채점된다.)

### 라운드를 늘리면 생기는 일 (= 2라운드는 반드시 채울 것)

4 대 1은 **짝지어지지 않은(unpaired) 불균형 설계**다. 1라운드에서 멈추면:

- 대조군 런이 하나뿐이라 **직접학습 arm의 시드 분산을 측정할 수 없다.**
  그 한 런이 유난히 좋았는지 나빴는지는 이 데이터만으로 알 수 없다.
- 런 단위 검정에서 라벨을 바꿔 배치하는 경우의 수가 C(5,1) = 5가지뿐이라
  **얻을 수 있는 최소 p값이 0.2**다. 즉 데이터가 아무리 깨끗해도 p<0.05에
  **원리적으로** 도달할 수 없다.

라운드를 하나 더 돌리면 이게 바로 풀린다. 1인 1런씩 추가할 때의 하한:

| 라운드 | 커리큘럼 런 | 직접학습 런 | 런 단위 최소 p |
|---|---|---|---|
| 1 | 4 | 1 | 0.20 (p<0.05 불가) |
| **2** | **8** | **2** | **0.022** |
| 3 | 12 | 3 | 0.0022 |
| 4 | 16 | 4 | 0.0002 |

즉 **2라운드가 이 실험의 손익분기점**이다. 그리고 그중에서도 가장 값어치가
큰 한 판은 **직접학습 arm의 두 번째 런**이다 — 그게 생기기 전까지는 대조군
점수 중 얼마가 시드 운인지 아무도 계산할 수 없다 (대조군은 혼자 채우는
arm이라 항상 병목이다). `analyze.py`가 시드 현황 밑에 현재 런 수와
그때의 최소 p를 매번 찍어 주니, 지금 어디쯤인지는 그걸 보면 된다.

**어느 라운드에서 멈추든 결론 문장은** "커리큘럼이 유의하게 낫다"가 아니라
**"효과 크기가 얼마이고, 그것이 시드 운으로 설명되는 범위 안인가 밖인가"**로
쓰는 편이 안전하다. 런이 몇 개든 5~20개 규모에서 나오는 p값은 관문이 아니라
방향이다.

라운드를 못 늘릴 때를 대비해 도구에 들어가 있는 보완책 (전부 자동):

1. **예산 일치 지점 3개** — 끝점 하나만 보지 않는다. 단, 세 지점은 **같은 5개
   런을 세 번 들여다본 것**이지 독립 반복이 아니다. 그리고 `early`는 애초에
   같은 방향이 나올 자리가 아니다(커리큘럼은 아직 발전기·탈출구를 못 봤으니
   바닥이 정상이다 — 1단계의 *비용*을 보는 칸이다). 실제로 헤드라인 방향을
   보강해 줄 수 있는 건 `mid`와 `final` 둘뿐이고, 그 둘조차 상관된 관측이다.
2. **학습 곡선** — 곡선 5개는 점 5개보다 노이즈에 훨씬 덜 휘둘린다.
3. **매치드 에피소드 검정** — 모든 런이 **같은 고정 에피소드 시드**를
   플레이하므로, 커리큘럼 런 하나하나를 대조군 런과 에피소드 단위로 짝지어
   비교할 수 있다 (승패는 McNemar, 발전기 수는 부호검정). 4개 비교가 전부
   같은 대조군 런을 재사용하므로 **독립 반복이 아니며**, Holm 보정을 걸고
   그 한계를 출력에 같이 적는다.
4. **n=1 caveat** — 커리큘럼 arm에서 측정된 시드 SD를 빌려서 "런 하나를 더
   돌리면 커리큘럼 평균에서 ±얼마 안에 떨어질 것"이라는 95% **예측구간**을
   그리고, 관측된 차이가 그 안인지 밖인지를 말해 준다. 폭은
   `t(n-1) × SD × √(1 + 1/n)`이고 n=4에서 **3.56 × SD**다 — 흔히 쓰는
   1.96 × SD가 아니다 (비교 대상이 "4런 평균 − 1런"이고 SD 자체도 4런에서
   추정한 값이라, 1.96을 쓰면 폭이 1.8배 좁아져 노이즈를 결과로 착각한다).
   **런 단위**에서 이 설계가 지지할 수 있는 가장 강한 문장이 그거다
   (직접학습 arm의 SD가 커리큘럼 arm과 비슷하다는 가정이 깔려 있고, 그
   가정은 이 데이터로 검증할 수 없다는 점도 같이 적을 것).
5. **페어드 검정 (옵션)** — 시드 블록이 사람마다 독립이라 계획된 런에서는
   양쪽 arm에 다 있는 시드가 없고, 따라서 페어드 검정은 꺼져 있다. 손해는
   거의 없다 — 페어드 부호뒤집기 검정의 하한은 2/2^k라 페어 2개면 0.5,
   3개여도 0.25로 **옆에 나란히 찍히는 비페어드 검정(2라운드 0.022)보다
   훨씬 약하다.** 그래도 굳이 원하면, 남는 밤에 **반대편 arm을 이미 쓰인
   시드로** 한 번 돌리면 페어가 하나 생기고 2개가 되는 순간 `analyze.py`가
   자동으로 켠다. 표에 없는 시드로 돌려도 버려지지 않는다 — arm이 넓어진다.

### 시작 전 파일럿 (1명, 30분) — 건너뛰지 말 것

**Lv3는 어렵다.** 이미 측정해서 `results/`에 커밋해 둔 기준선(각 200
에피소드, 공용 프로토콜):

| 기준선 | 승률 | 발전기 (평균 ±1.96 SEM) |
|---|---|---|
| 랜덤 정책 | **0%** | 0.03 ±0.02 |
| 손으로 쓴 FleePolicy | **0%** | 2.25 ±0.12 |

즉 **손으로 쓴 정책조차 200판에서 한 번도 탈출하지 못한다.** 학습된 정책
둘 다 승률 0%로 끝나면 헤드라인 지표가 바닥에 붙어 실험이 두 arm을 전혀
구별하지 못한다. 대조군 런이 하나뿐인 이번 설계에서는 바닥 효과가 더
치명적이다 — 검정력이 이미 낮은데 지표까지 안 움직이면 남는 게 없다.
그래서 `analyze.py`는 기본값이 `--metric all`이고, 세 지표를 한 번에
찍는다.

**단, 맵이 불가능한 게 아니다 — 어려운 건 상대다.** 같은 FleePolicy를 약한
상대(Mansion에서 학습된 PPO 술래)에 붙이면 Lv3에서 **승률 73%, 발전기
4.70개**가 나온다 (30 에피소드). 즉 Lv3는 충분히 탈출 가능한 맵이고, 승률
0%는 휴리스틱 `ChasePolicy`가 그만큼 강한 추격자라는 뜻이다. 따라서
**발전기 개수를 줄이는 건 아마 잘못된 레버다** — 난이도의 원인은 맵이
아니라 상대이므로, 지표가 안 움직이면 `avg_missions`로 바꾸는 쪽이 맞다.

5번의 밤샘 학습을 태우기 전에 한 사람이 먼저 확인할 것:

```bash
# 짧은 파일럿: 직접학습 196,608 스텝만 (약 20~30분)
.venv/bin/python train.py --config configs/lv3_direct.json --seed 0 \
    --steps 196608 --out runs/pilot
.venv/bin/python evaluate.py --model runs/pilot/model.zip --tag pilot --episodes 50
```

파일럿 결과 판단:

- **승률이 0%를 넘는다** → 승률을 주 지표로 쓸 수 있다. 그대로 진행.
- **승률 0% + 발전기 수가 휴리스틱(2.25) 근처거나 그 이상** → 정상이다.
  진행하되 **주 지표를 `avg_missions`로** 쓸 것. 발전기 수는 0~5의 단계적
  지표라 승률이 바닥일 때도 두 arm을 구별하고, 에피소드 단위 부호검정도
  거기서만 의미가 있다. 승률은 보조로만 보고한다. (`analyze.py`는 기본으로
  셋 다 찍으므로 명령은 그대로 두고 **발표에서 어느 표를 헤드라인으로 쓸지**
  만 정하면 된다.)
- **발전기도 0~1개에서 멈춘다** → 팀 회의. 위에서 봤듯 맵 자체는 탈출
  가능하므로 발전기 개수를 건드리는 것보다 **상대를 약화시키는 쪽**이
  원인에 맞는 조치다 (예: `agents.py` `ChasePolicy`의 시야·속도, 또는
  `world.py`의 술래 rage 상한). 어느 쪽이든 **세 레벨에 동일 적용 +
  기준선 재측정 + 전원 같은 코드**가 조건이다.

기준선을 직접 다시 재려면 (랜덤 40초, 휴리스틱 약 9분):

```bash
.venv/bin/python evaluate.py --model random --tag random
.venv/bin/python evaluate.py --model heuristic --tag heuristic
```

### 멤버별 할 일

**본인 arm 하나만**, 아래 시드를 **왼쪽부터 하룻밤에 하나씩** 돌린다.
결과 JSON은 전원 같은 작업 트리에 모은다(`analyze.py`가 전원의 결과 파일을
한 번에 읽음).

기본 시드는 멤버 순서대로 1번부터 나간다:

| 멤버 | arm | 시드 순서 (1런/1밤) |
|---|---|---|
| `member1` | 커리큘럼 (단계별) | **1** → 11 → 21 |
| `member2` | **직접학습** (최종 맵에서 바로) | **2** → 12 → 22 |
| `member3` | 커리큘럼 (단계별) | **3** → 13 → 23 |
| `member4` | 커리큘럼 (단계별) | **4** → 14 → 24 |
| `member5` | 커리큘럼 (단계별) | **5** → 15 → 25 |

굵은 글씨가 1라운드(필수). 실행은 `scripts/run_curriculum.sh <시드>` /
`scripts/run_direct.sh <시드>`. 표가 다 떨어지면 자기 블록에서 계속 +10
하면 된다 (35, 45, …).

- **시드 블록은 사람마다 독립이다.** 본인 기본 시드 + 10의 배수만 쓰면
  누구와도 겹치지 않는다. 같은 arm에 같은 시드를 두 번 돌리면 설정도 시드도
  같으니 **글자 그대로 같은 런**이라 아무것도 늘지 않는다.
- **시드 0은 일부러 비워 뒀다.** `train.py --seed`의 기본값이라, `*_seed0`
  결과 파일이 보이면 누가 `--seed`를 빠뜨린 것이다 — `analyze.py`가 주인 없는
  파일로 잡아 준다.
- 스크립트가 시작 전에 "이 시드는 누구의 몇 번째 런"인지 찍어 주고, 남이
  이미 커밋한 결과 파일을 덮어쓰려 하면 **학습을 시작하기 전에** 멈춘다.
- **직접학습 arm(`member2`)은 한 사람이 혼자 채우므로 항상 병목이다.**
  1라운드만 끝난 상태에서 그 런이 발산하면 대조군이 통째로 사라진다.
  `runs/direct_seed*/progress.csv`의 `rollout/ep_rew_mean`이 계속 떨어지거나
  NaN이 뜨면 대조군 전체가 위험해진다. 그래서 **직접학습 2번째 런
  (seed 12)이 최우선**이었다.

이 표의 원본은 `configs/team.json`이다 (스모크 테스트가 "직접학습 1명 +
나머지 커리큘럼", "시드 전역 중복 없음", "기본 시드가 멤버 순서대로
연속", "시드 0 미사용"을 검사한다).

```bash
# 준비 (레포 루트에서 한 번)
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python tests/test_smoke.py        # 전부 통과해야 시작

# 커리큘럼 arm — 세 단계 학습 + 평가 3지점 + 학습곡선까지 한 줄
scripts/run_curriculum.sh 1

# 직접학습 arm — 한 번 학습 + 같은 3지점 + 학습곡선
scripts/run_direct.sh 2
```

단계를 손으로 돌리고 싶으면 스크립트 안의
세 줄을 그대로 복사하면 된다 (Lv2부터는 `--init <이전 단계>/model.zip`이
가중치 이전의 전부다).

유용한 환경변수: `CURVE=0` (학습곡선 생략), `CURVE_EVERY=2` (스냅샷 절반만
채점 — early/mid/final과 양 끝점은 항상 유지된다), `CURVE_EPISODES=30`
(곡선 점당 에피소드 수), `PY=<python>` (venv를 직접 관리할 때), `FORCE=1`
(이미 있는 결과 파일을 덮어쓸 때만).

**중간에 끊겼을 때 (크래시/절전)**: `runs/.../checkpoints/`의 마지막 스냅샷
파일명에 **누적** 스텝 수가 들어 있다 (예: `ppo_688128_steps.zip`). 그
스냅샷을 `--init`으로 주고, `--steps`에 아래 목표 누적에서 파일명 숫자를 뺀
값을 넣어 같은 `--out`으로 다시 돌리면 예산이 정확히 이어진다:

| 단계 | 목표 누적 스텝 |
|---|---|
| lv1 | 393,216 |
| lv2 | 983,040 |
| lv3 / 직접학습 | 1,998,848 |

```bash
# 예: 커리큘럼 seed 1이 lv2 도중 688,128 누적에서 끊겼다면
# (983,040 - 688,128 = 294,912)
.venv/bin/python train.py --config configs/lv2.json --seed 1 \
    --init runs/curriculum_seed1/lv2/checkpoints/ppo_688128_steps.zip \
    --steps 294912 --out runs/curriculum_seed1/lv2
```

스냅샷은 98,304 스텝(롤아웃 6개)마다 저장되므로 이 뺄셈은 항상 롤아웃
단위로 떨어진다. 어긋난 값을 주면 train.py가 **학습을 시작하기 전에** 멈추고
올바른 계산법을 알려준다 (밤새 돌린 뒤 아침에 알게 되는 일은 없다). 기존
`progress.csv`는 `progress_1.csv`로 이름이 바뀌어 보존된다.

이어서 돌린 뒤 남은 단계는 스크립트 대신 손으로 돌리면 되고, 마지막에 평가
세 줄만 챙기면 된다 (커리큘럼이면 `lv3/model.zip` → `curriculum_seed<N>`,
`lv2/model.zip` → `curriculum_mid_seed<N>`, `lv1/model.zip` →
`curriculum_early_seed<N>`).

끝나면 본인 arm의 결과 JSON **세 개**(early / mid / final)와 학습곡선 JSON
한 개가 생긴다 — **이 파일들이 런의 결과 기록이다**. 에피소드별 결과까지 들어 있지만
작은 파일이다. `runs/`는 용량 때문에 gitignore; 모델 zip은 로컬에 보관.
`analyze.py`가 맨 위에 **시드 현황**(어느 시드의 어느 지점 결과가 있는지)을 찍는다.

### 결과 분석

결과가 모이면:

```bash
.venv/bin/python analyze.py                        # 기본: 세 지표 전부
.venv/bin/python analyze.py --metric avg_missions  # 발표용 한 지표만
```

출력:

- **시드 현황** — `configs/team.json` 기준으로 어느 시드의 어느 지점 결과가
  있는지. 런이 5개뿐이라 하나가 빠지면 실험의 20%가 빈다
- **기준선 두 줄** (random / heuristic) — 학습된 정책이 무엇을 이겼는지
  볼 수 있는 참조점
- **런별 표 + Wilson 95% 신뢰구간** — 200 에피소드 평가의 이항 노이즈가
  ±0.07쯤 된다는 걸 숫자로 보여준다 (리뷰어가 반드시 묻는 것). arm마다
  **시드 간 SD**도 같이 찍는데, 직접학습 arm은 n=1이라 "측정 불가"로 나온다
  — 그게 이 설계의 핵심 한계이므로 표에 그대로 남겨 둔다
- **비페어드 순열검정 + 그 하한** — 라벨 배치가 5가지뿐이라 최소 p가 0.2다.
  스크립트가 "이 설계는 p<0.05에 도달할 수 없다"를 매번 같이 출력하므로,
  유의성 대신 **효과 크기**로 이야기하면 된다
- **대조군의 순위** — 5개 런 중 직접학습 런이 몇 번째인지 (동점 처리 포함).
  4대1 순열검정을 사람이 읽을 수 있는 형태로 바꾼 것
- **leave-one-run-out 범위** — 런 하나를 빼면 방향이 뒤집히는지. 커리큘럼
  시드뿐 아니라 (스페어 런이 있으면) 직접학습 런도 빼 본다. 뒤집히면
  승자를 말하면 안 된다
- **n=1 caveat 밴드** — 커리큘럼 arm의 시드 SD로 만든 95% 예측구간
  (`t(n-1)×SD×√(1+1/n)`, n=4면 3.56×SD)과 관측된 차이를 비교해 준다
- **매치드 에피소드 검정** — 커리큘럼 런 하나하나 vs 대조군 런을 에피소드
  단위로 (승패는 McNemar, 발전기 수는 부호검정) 비교하고 Holm 보정. 4개
  비교가 같은 대조군을 재사용한다는 경고도 같이 찍는다
- **페어드 검정 (자동, 기본은 꺼짐)** — 스페어 런으로 양쪽 arm에 다 있는
  시드가 2개 이상 생기면 부호뒤집기 순열검정이 추가로 켜진다
- **학습 곡선 표** — 두 arm을 같은 누적 스텝 축에 올린 표 (아래)
- **주인 없는 결과 파일 경고** — `results/`에 있는데 어느 비교 세트에도 안
  잡히는 파일 (`--tag`를 잘못 줬거나 예산 격자에 없는 스냅샷)

**비교 세트가 자동으로 잡힌다** (모두 같은 Lv3 프로토콜):

1. **early** (393,216 스텝) — 커리큘럼이 Lv1만 끝낸 시점. 발전기도 탈출구도
   아직 못 봤으니 바닥에 가까운 게 정상이다. 이 점은 커리큘럼의 **비용**을
   보여주는 자리다 (직접학습은 같은 예산을 전부 Lv3에 썼다)
2. **mid** (983,040 스텝) — 커리큘럼이 Lv1+Lv2를 막 끝낸 시점, 즉 **Lv3
   경험이 0인** 모델 vs 같은 예산을 전부 Lv3에 쓴 모델.
   해석: 중간지점이 **비슷하면** 커리큘럼의 이점은 Lv3 샘플 효율 이야기고,
   중간지점에서 **커리큘럼이 크게 앞서면** 단순화된 레벨에서 진짜 전이가
   일어났다는 뜻이다
3. **final** (1,998,848 스텝) — 헤드라인
4. **vsppo** — 보류 상대 평가 (아래, 선택)

세 지점 모두 스크립트가 자동으로 채점하므로 추가 학습이 필요 없다
(393,216과 983,040은 직접학습 arm의 체크포인트 격자에 정확히 맞고, 스크립트가
그 숫자를 `configs/`에서 직접 읽어 스냅샷 이름을 만든다).

**학습 곡선**: `results/curve_*.json`이 있으면 `analyze.py`가 맨 마지막에
두 arm을 같은 x축(누적 env 스텝)에 올린 표를 찍는다 — 커리큘럼 4개 평균 vs
직접학습, 행마다 몇 개 런의 평균인지(`n=`)와 early/mid/final 지점 표시까지.
이 실험에서 정보량이 가장 큰 그림이고, 커리큘럼 곡선의 Lv1/Lv2 구간이
평평하다가 Lv3 진입에서 얼마나 빨리 따라잡는지가 한눈에 보인다.

발표용 그래프를 그릴 때는 tidy CSV로 뽑아서 아무 도구에나 넣으면 된다:

```bash
.venv/bin/python analyze.py --curve-csv curves.csv
# arm,seed,train_steps,win_rate,escape_rate,avg_missions,avg_steps
```

**보류 상대(held-out opponent) 평가** (선택): 두 arm 모두 학습 때와 똑같은
`ChasePolicy`로 평가되므로, 지표가 "Lv3를 배웠다"와 "이 스크립트 상대의
습관을 이용하는 법을 배웠다"를 구분하지 못한다. 학습에서 본 적 없는 상대로
한 번 더 재보면 그 구분이 된다:

```bash
# 커리큘럼 arm (예: seed 1)
.venv/bin/python evaluate.py --model runs/curriculum_seed1/lv3/model.zip \
    --opponent model:ppo_tagger_mansion.zip --tag curriculum_vsppo_seed1
# 직접학습 arm (seed 2)
.venv/bin/python evaluate.py --model runs/direct_seed2/model.zip \
    --opponent model:ppo_tagger_mansion.zip --tag direct_vsppo_seed2
```

`analyze.py`가 `*_vsppo_seed*`를 별도 비교 세트로 자동 인식한다.
(커리큘럼 쪽만 재면 arm 하나뿐이라 비교가 안 되므로, 이걸 할 거면
**직접학습 arm도 반드시 같이** 재야 한다.)

모델 zip은 용량 때문에 git에 없고 릴리스 `mansion-artifacts-v1`로 배포한다
(받는 명령은 저장소 README의 Usage 참고).

**한계 (측정해 봄)**: 이 술래는 Mansion(여러 방·문·미션 3개, 아이템 ON)에서
학습된 모델이라 Lv3에서는 약하다. FleePolicy 기준 이 술래 상대로는 승률
73%인데 프로토콜의 `ChasePolicy` 상대로는 0%다. 즉 **더 어려운 상대가 아니라
더 쉬운 상대**이므로, 두 arm 모두 천장에 붙어 구별이 안 될 가능성이 크다.
"학습에서 본 적 없는 상대"라는 점은 유효하지만, 여기서 나온 차이는 프로토콜
상대에서 나온 차이보다 약한 근거로 취급할 것.

**샘플 효율 곡선** — `scripts/run_*.sh`가 마지막에 자동으로 돌리므로 따로 칠
일은 보통 없다. 곡선만 다시 뽑거나 (`CURVE=0`으로 건너뛴 뒤) 나중에 돌릴 때:

```bash
.venv/bin/python evaluate.py --curve runs/curriculum_seed1 --episodes 50 \
    --tag curve_curriculum_seed1
.venv/bin/python evaluate.py --curve runs/direct_seed2 --episodes 50 \
    --every 2 --tag curve_direct_seed2     # --every 2 = 절반만 채점
```

커리큘럼 곡선에는 Lv1/Lv2 단계의 스냅샷도 포함된다 — "Lv1을 배우는 동안
Lv3 성적이 이미 오르는가"가 그래프 하나로 보인다. 곡선 원자료는
`results/curve_*.json`.

주의: 실험 결과를 서로 비교해야 하므로 `configs/`, `train.py`의 `DEFAULTS`,
`evaluate.py`의 프로토콜은 **전원 합의 없이 바꾸지 않는다.** 시드만 다르다.
